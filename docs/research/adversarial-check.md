# Independent attack: IIIF migration/regression auditor

Research date: 2026-10-15. This pass searched broad web and GitHub-indexed results for IIIF manifest diff, manifest-diff, semantic diff, migration comparison, regression testing, QA, corpus checking, and current official tool inventory. Direct GitHub search pages could not be fetched through the web tool; this is a search limitation, not evidence of absence.

## Verdict

No inspected product provides the proposed whole workflow: pair before/after manifest corpora, compare v2/v3 meaning with explicit identity-rewrite policy, flag losses in content/navigation/rights/metadata/services, produce reviewable reports, and gate CI. The candidate survives this independent competition attack. Claim **a specialized gap in existing tooling**, not first-ever or proven absence of competitors. The strongest alternative is a competent developer composing @iiif/parser conversion with JSON snapshots, generic diff and institution-specific test scripts. Be materially better than that in diagnostic precision, safe identity pairing, actionable reports and setup effort.

Demand is credible for migration/metadata QA generally, but not proven for a particular IIIF-only product. No user interviews were performed. A polished first release should state its exact coverage and facilitate users testing their own corpus quickly.

## Strong primary evidence for pain and the current workaround

1. [Stanford Digital Repository, “Strategies for Digital Library Migration,” April 21 2023](https://journal.code4lib.org/articles/17290). Important: Stanford, not Harvard. Describes bugs despite unit tests and staging because metadata heterogeneous; develops before/after roundtrip tests on typically 100k actual digital objects per mapping change, normalized source/target data, per-object diffs, parallel runs and summary statistics. Notes custom tooling removed after migration. This is not IIIF-specific, but it demonstrates the exact engineering workaround and that schema validity alone fails to catch mapping mistakes. Do not spend >200 words derived from this source in a public summary without higher allowance.
2. [University of Leeds Libraries, March 27 2026](https://leedsunilibrary.wordpress.com/2026/03/27/open-content-migration-completed/). Migration of ~400k files; testing/review/normalization framework required for rights metadata; bespoke Flask migration app with dashboard built for urgent but short-lived need. IIIFBuilder consumes preservation API plus catalogue metadata to generate manifests. Supports a disposable local/static audit tool and CI use; weakens a heavyweight enduring hosted-platform pitch.
3. [Omeka Forum, May 30 2024](https://forum.omeka.org/t/impact-of-default-cors-option-in-iiifserver-module-configuration/22721). IIIFServer configuration regression disabled CORS and silently restricted browser-client use of distributed IIIF resources. This is a real post-change IIIF failure, but offline manifest semantic checks alone cannot detect it. Do not claim this incident would be caught unless network/browser header checks are implemented.
4. [Bodleian manifest server](https://github.com/bodleian/iiif_manifest_server) documents header-driven host rewrites for staging/QA and v2/v3 content negotiation; its unit tests refer to institution-specific UUIDs. This is direct evidence that identity rewrite policy matters and conformance is not enough.
5. [Official v2/v3 content negotiation recipe](https://iiif.io/api/cookbook/recipe/0057-publishing-v2-and-v3/) explicitly supports both versions at one URI, defaults/fallbacks and clients encountering inconsistent server capabilities. Snapshot evidence must preserve requested/returned versions if network acquisition is added.

## Material feasibility / trust risks to resolve

- **Version detection:** v4 resources now appear in official tools/cookbook. Reject unsupported contexts/types clearly. Never let a v4 or collection silently produce an empty “unchanged” v3 result.
- **No false green from lossy normalization:** a parser converting both sides can discard the same unsupported original field, making a loss invisible. Retain source locations and report unsupported properties/constructs explicitly; green means assessed checks pass, with coverage stated.
- **v2 sequences:** v2 allows multiple sequences; v3 centralizes canvases. Comparing only the first sequence conceals loss. Reject or flag extra sequences rather than flatten ambiguously.
- **Identity:** position-based canvas matching turns reordered pages into false modifications or silently pairs different pages. Require stable identities or explicit rewrite rules; ambiguous/duplicate matches must be blockers. Rewrite rules should be anchored URL prefixes/maps, not arbitrary regex that conflates records. Unmatched candidate files cannot be ignored.
- **Target meaning:** annotation targets can be strings, objects, lists and selectors; image body may be Choice or SpecificResource. Declared static-image scope still requires either proper handling or a visible unsupported finding.
- **Metadata:** order can be significant for displayed metadata; multiple language values, repeated labels and HTML must not collapse into dictionaries or plain stripped text. License/rights and requiredStatement/attribution need exact documented conversion rules.
- **Service URLs:** Image API v2 `full/full` and v3 `full/max` can represent equivalent requested content only with known service versions. Do not blanket-normalize suffixes; don't infer pixels unchanged just because service URL matches.
- **Ranges:** nested/repeated ranges and external range references need bounded handling; compare order and membership, not labels alone. External resources are unassessed unless fetched/snapshotted.
- **Scope honesty:** link equality does not verify linked OCR/search/annotation contents, HTTP reachability, CORS, viewer behaviour, pixels, auth or privacy. Report “link preserved,” not “OCR preserved” if contents not inspected. A separate optional bounded network check can add more evidence later.
- **Security:** user-controlled metadata can contain HTML and JS-like URLs. Reports must escape/sanitize rendered values, never execute manifest scripts/HTML, and avoid embedding untrusted remote images automatically. Remote acquisition needs SSRF/timeouts/redirect/size/count limits if provided.
- **Performance:** 100k-manifest corpus is realistic from Stanford's experience; stream/one-pair-at-time, cap individual files/depth, avoid one giant interactive DOM. Summary must count skipped/error/unpaired cases rather than hide them.

## Acceptance test ideas for independent QA

Seed a corpus with: equivalent v2/v3 pair; removed final canvas; reordered equal-count canvases; changed image body while metadata stays identical; lost non-English label; duplicate metadata labels; rights loss; requiredStatement edit; altered nested range member; changed OCR/search link; `Choice`/SpecificResource; multi-sequence v2; duplicate IDs; ambiguous mapping; malformed/oversized JSON; unsupported v4; `<script>` and `javascript:` values. Every mutation should have a precise reason/path or explicit unsupported status, and no silent pass. Compare original source paths in report to raw JSON. Test packaged CLI installation and actual CI failure exit, not just library functions.
