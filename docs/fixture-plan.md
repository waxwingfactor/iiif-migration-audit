# Independent fixture and acceptance plan

Prepared 2026-10-15, before inspecting the comparator implementation. This plan defines user-observable preservation assertions, not tests that merely mirror extractor functions. Every release must distinguish unexpected changes, reviewed intentional changes, and incomplete coverage.

## Evidence and attribution rules

Use the original JSON bytes as source evidence; write expected invariants independently from the IIIF specifications and human inspection. Do not generate an expected v3 document or expected audit result through the converter or comparator under test. A handwritten v3 companion to a v2 fixture must be labeled as a project-authored adaptation, with a short mapping rationale reviewed by another person/agent.

The [IIIF Presentation 3 specification](https://iiif.io/api/presentation/3.0/) identifies its editors/contributors and links to [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). The [IIIF API source contribution policy](https://github.com/IIIF/api#contributions) states that contributions can be published under CC-BY. Keep external samples separately attributed; the project MIT license must not replace their terms. Recipe images can have different rights (for example, the Whistler image is identified as public domain, the John Dee examples identify Wellcome CC BY-NC 4.0, and recipe 0008 declares CC BY-SA 3.0). Vendor JSON evidence only, preserve all embedded rights/attribution, and do not download image pixels. If a JSON source has a more specific notice or unclear provenance, preserve that notice or use a project-authored synthetic specimen instead of asserting MIT coverage.

Each vendored source needs a provenance record with upstream URL, exact requested Accept header, final URL, retrieval date, raw-byte SHA-256, source title, attribution/license statement and its evidence link, expected Presentation context, and whether bytes were modified. Modified fixtures retain their source citation and list the deliberate edits. Refresh fixtures intentionally in review; live upstream URLs must not be CI test dependencies.

Suggested external-sample notice: “IIIF Presentation API examples and cookbook recipes, IIIF Consortium, editors and contributors; source URLs and retrieval details in provenance records. Used/adapted with attribution under the source terms. Referenced collection objects and images retain their own rights. No endorsement is implied.”

## A verified official cross-version pair

The [0057 dual-publication recipe](https://iiif.io/api/cookbook/recipe/0057-publishing-v2-and-v3/) is the strongest small truth fixture. On 2026-10-15 the following two requests were independently made against the same address and returned different requested contexts and Content-Type profiles:

```text
URL: https://iiif.io/api/cookbook/recipe/0057-publishing-v2-and-v3/manifest.json
Accept: application/ld+json;profile="http://iiif.io/api/presentation/2/context.json"
context: http://iiif.io/api/presentation/2/context.json
raw bytes: 1355
SHA-256: 91d667485d84ed5e5eb933b6ebd7b4eb5d1fcc4693acd7f2cc59e1397399fc7b

URL: https://iiif.io/api/cookbook/recipe/0057-publishing-v2-and-v3/manifest.json
Accept: application/ld+json;profile="http://iiif.io/api/presentation/3/context.json"
context: http://iiif.io/api/presentation/3/context.json
raw bytes: 1313
SHA-256: 57ee56bc6b8628e0b26c9c61c0a4a28d22832cd5683d0f75175435ca03fcb40b
```

Independent invariants: one canvas; preserved manifest ID and canvas ID; coordinate space 1200 wide × 1800 high; one PNG image with identical resource URL and pixel dimensions; full-canvas painting target; identical title text. Keep identifiers byte-for-byte in this fixture: stability matters for existing annotations. Source v2 title is untagged while v3 asserts English, so language-tag addition must be visible or explicitly documented as an expected difference. Neither canvas has a label. A generic v2 Sequence wrapper/label is not automatically equivalent to a v3 content Range; any uncovered sequence metadata must remain visible. Do not force this pair to return zero findings by weakening checks.

This pair is a preservation smoke test, not proof of complete conformance or universal conversion fidelity. Pin both HTTP responses separately. An importer that retrieves the same response twice must fail the expected-context assertion rather than reporting a meaningful cross-version success.

## Independent expected records

Keep one small, readable expected record per source, manually recording canvas IDs in reading order, labels with every language and repeated value, dimensions, ordered painting resource IDs/targets, service identity/profile, root and granular descriptive fields, rights/required statement, link roles and full descriptors, and nested range membership. Include source JSON pointers so reviewers can verify each expectation without trusting the extractor. Store absent, empty and unexamined states separately.

Use the [Presentation 3 change log](https://iiif.io/api/presentation/3.0/change-log/) as a mapping rationale, not a conversion oracle. In particular `description→summary`, `related→homepage`, multiple Sequence alternatives and Range extent can change meaning. Identity preservation and equivalent pixels are different assertions. A URL rewrite policy can authorize the former change but cannot prove that the server supplies the same image.

## Mutation and negative-control corpus

Each mutation starts from independently inspected bytes, modifies one stated property, and has a handwritten expected observable finding. Test the same fixture through the public CLI, JSON report, portable HTML and browser interface. Exact finding codes can evolve; the necessary user-observable loss cannot.

| Family             | Regression specimens that must be visible                                                                                                            | Negative controls / safety assertions                                                                                                                                                             |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pages              | Delete first/middle/last canvas; add unexpected page; duplicate Canvas ID; swap page order; swap only images while labels remain                     | Legitimate duplicate labels survive. Reformat JSON/object key order without changing array order should not create content regressions.                                                           |
| Text               | Remove one language; drop one of multiple values; empty a title; alter canvas label; drop one repeated metadata entry; reorder metadata              | All source languages and values retained. Preserve ordered metadata, distinguish missing/empty. Do not invent semantic equivalence by stripping arbitrary markup or normalizing Unicode silently. |
| Rights             | Remove/alter license, required statement, value language or statement label; change rights on image/canvas while root stays same                     | Root rights and granular rights are separate. Any legal/rights conclusion is out of scope; the audit reports preservation of assertions.                                                          |
| Image/painting     | Change image URL/service/profile/dimensions/format; drop one painting; reverse painting order; change fragment coordinates                           | Canvas/image dimensions may differ validly. Keep service API declaration changes visible; same basename is not image identity.                                                                    |
| Navigation         | Drop/flatten/reorder range; alter leaf target; introduce unknown canvas reference; change start; change direction or paging                          | Keep IDs, labels, range order and membership separate. Start p2 still leaves p1 in the sequence. Graph cycle must terminate with a diagnostic.                                                    |
| Links              | Remove OCR page, rendering, homepage, seeAlso or thumbnail; retain URL but change format/profile/label                                               | Report preserved reference without claiming remote body/availability verification. No implicit fetches from source URLs.                                                                          |
| Pairing            | Missing old/new file; extra candidate; same basename in nested folders; duplicate pair key; duplicate map entry; typo in explicit map                | Every input is accounted for exactly once or reported. No arbitrary first-match wins. A reordering cannot be disguised by position-based pairing.                                                 |
| Rewrite policy     | Expected host move for image/download, unexpected Canvas-ID move, overlapping prefix rules, unchanged URLs that coincidentally contain old host text | Only exact/prefix rules with explicit scope apply; show raw and compared values. Rewriting body text or the wrong role is unacceptable.                                                           |
| Review policy      | Approve one precise intentional change; add an unrelated regression; stale approval; malformed scope; blank reason                                   | Approved evidence remains in report, new regression fails, stale entry warns. Broad ignores must not hide incomplete extraction.                                                                  |
| Unsupported inputs | Multiple v2 sequences; external range without supplied body; Choice/SpecificResource selector/AV/custom extensions if not supported; v4 context      | No clean verdict after silently dropping content. Supported checks may still run, but verdict and totals clearly state incomplete coverage.                                                       |
| Robustness         | Invalid JSON, JSON root null/array/number, missing context/type, malformed arrays, extremely deep nested ranges, cyclic references, oversized values | Structured diagnostic, bounded work and nonzero CLI result. No stack trace as the sole user message; no partial report presented as complete.                                                     |
| Report security    | Labels/IDs containing closing script tags, HTML handlers, JavaScript/data URLs, quotes, ampersands, unusual Unicode; hostile filenames               | All source values stay inert in UI/HTML. No network request or script from input, no unsafe clickable scheme, no report escaping its chosen output directory.                                     |

Property/metamorphic assertions add value beyond fixtures: comparing supported document to itself has no differences; changing only JSON object key order preserves findings; reversing before/after swaps added/removed consistently; explicit policies do not mutate inputs; repeated runs yield stable finding identity/order; moving an unrelated pair in the corpus does not change an existing approval's target.

## Release performance and resource gates

These are proposed acceptance targets, not measurements or advertised capabilities. Record hardware, Node/browser version, fixture size, time, peak memory and generated report size before deciding the supported limits. Use deterministic synthetic documents modeled on the public book; never download image bytes for benchmarks.

- **Normal review:** 100 manifest pairs × 100 canvases, plus multilingual text and ranges. Local CLI completes within 10 seconds on the test laptop, uses at most 512 MiB RSS, and reports every pair. Browser upload/analysis remains interactive and finishes within 15 seconds for an explicitly documented input-size allowance.
- **Institutional batch:** 1,000 pairs × 100 canvases (100,000 pages); target 60 seconds and 1 GiB peak RSS for CLI. Process pairs incrementally rather than retaining both full corpora plus all normalized snapshots. Report concise counts and paginated findings; do not dump duplicate entire JSON documents into every finding.
- **Large object:** one 10,000-canvas manifest pair; target 15 seconds and 512 MiB RSS. Reversing all pages must not trigger quadratic alignment behavior. A many-to-many ambiguous ID case must produce an explicit diagnostic with bounded work.
- **Large findings:** 10,000 changes: report opens and filters within two seconds after local file load on the test browser; pagination/virtualization prevents 10,000 heavyweight DOM cards. Counts and exported JSON must retain all findings even if the visible list is paginated.
- **Input guardrails:** publish actual tested per-file/total limits separately for browser and CLI. Exceeding a limit is a clear incomplete/error result, not a skipped input. Test immediately below/above each configured cap and depth bound. A browser cap is not a CLI claim.
- **CI practicality:** ordinary correctness/security suite should remain comfortably below one minute. Keep benchmark smoke cases small and deterministic; record the larger benchmarks in release validation rather than creating flaky wall-clock tests on shared CI runners. Test cancellation/error cleanup with a temporary directory and confirm original inputs are byte-identical afterward.

If measured targets are missed, investigate algorithmic causes and narrow the documented supported limits honestly. Do not hide slow/skipped files, truncate finding totals, or relabel incomplete checks as a clean audit.

## Black-box acceptance scenarios

1. A library exports old v2 and regenerated v3 directories. Pair renamed manifests explicitly, authorize only an image-host migration, and find one missing page, one French title loss and one dropped attribution. Report all three with both file paths and pointers; CI fails; approval of the known title edit retains its evidence and leaves the other two failures.
2. Same-version generator upgrade: v3 book has unchanged IDs but images on two pages are swapped. The product must find changed image assignments even though canvas count and page labels match.
3. A static-image collection includes one Choice object and an unresolved external Range. Either fully check those constructs or mark the relevant scope incomplete; the corpus cannot receive a blanket clean verdict.
4. Run only from the packed distribution in a fresh directory, without repository source or network. CLI help, sample command, JSON output and standalone HTML work; importing that JSON into the browser preserves finding identities/counts. HTML remains usable without a server or CDN.
5. A non-developer reviewer opens the portable report, finds the worst affected object, filters to page/rights losses, inspects before/after evidence, and understands which changes still require a decision. Keyboard navigation and visible focus work; narrow viewport does not hide verdicts or controls.

The release evidence should state what was measured, what is supported, which fixtures remained incomplete, and any known limitations. It should never imply live-image, server/CORS/authentication, or viewer rendering equivalence from offline JSON checks alone.
